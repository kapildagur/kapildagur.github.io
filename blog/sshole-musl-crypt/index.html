SSHole: how a crypt() error let disabled passwords log in to sshd on musl

An account with no password should never accept one. On some Alpine servers it did, because an error string from the C library looked exactly like a disabled password.

On 5 November 2026, OpenSSH released 10.6p2 with one change: a workaround for a password authentication bypass on Linux systems that use musl libc with PAM disabled. Alpine shipped patched packages the same day. The bug is tracked as CVE-2026-123158, and SAFE Security named it "SSHole" and rated it 8.1 (High). It was reported by Özgün Kültekin of Wakefield.

The advisories tell you to upgrade, and you should. I also wanted to know why it happened, so I read the code on both sides, sshd and musl, and ran musl's crypt() myself. The bug is small and easy to follow, and it carries a lesson for anyone who writes code that returns error values.

Who is affected

All of these have to be true:

ConditionHow to check
OpenSSH older than 10.6p2, or an Alpine package older than the fixed one for its branchsshd -V, apk list --installed 'openssh*'
sshd is linked against musl libcls /lib/ld-musl-*
sshd does not use PAM: built without it, or UsePAM nosshd -T | grep -i usepam prints nothing or usepam no
Password authentication is onsshd -T | grep -i passwordauthentication
An account that may log in has * as its password fieldsee Checking your systems
Another account has a SHA-256 ($5$) or SHA-512 ($6$) password hashsee Checking your systems

Alpine is the obvious case: it uses musl, and its default openssh-server package is built without PAM. Alpine also ships openssh-server-pam, but on Alpine 3.22 that build still defaults to UsePAM no, so it takes the same code path unless you turn PAM on. Containers built on Alpine and small appliances built on musl are the other places to look. Distributions built on glibc, such as Debian, Ubuntu and RHEL, are not affected, and the reason why is one of the more interesting parts of this story.

What the password field holds

The second field of each line in /etc/shadow holds either a password hash or a marker that says there is no usable password:

ValueMeaning
$6$salt$hashA SHA-512 crypt hash. $5$ is SHA-256, $1$ is MD5, $2b$ is bcrypt.
*No password has ever been set. Password login is impossible because no input can hash to *.
! or ! followed by a hashThe account is locked, usually by passwd -l.
emptyNo password at all. sshd refuses this unless PermitEmptyPasswords is on.

The * marker rests on one assumption: no password can ever hash to *. That is true as long as crypt() only ever returns real hashes. On musl, it does not.

How sshd checks a password without PAM

Without PAM, OpenSSH portable checks passwords itself, in sys_auth_passwd() in auth-passwd.c. This is the function exactly as it stood before the fix:

int
sys_auth_passwd(struct ssh *ssh, const char *password)
{
    Authctxt *authctxt = ssh->authctxt;
    struct passwd *pw = authctxt->pw;
    char *encrypted_password, *salt = NULL;

    /* Just use the supplied fake password if authctxt is invalid */
    char *pw_password = authctxt->valid ? shadow_pw(pw) : pw->pw_passwd;

    if (pw_password == NULL)
        return 0;

    /* Check for users with no password. */
    if (strcmp(pw_password, "") == 0 && strcmp(password, "") == 0)
        return (1);

    /*
     * Encrypt the candidate password using the proper salt, or pass a
     * NULL and let xcrypt pick one.
     */
    if (authctxt->valid && pw_password[0] && pw_password[1])
        salt = pw_password;
    encrypted_password = xcrypt(password, salt);

    /*
     * Authentication is accepted if the encrypted passwords
     * are identical.
     */
    return encrypted_password != NULL &&
        strcmp(encrypted_password, pw_password) == 0;
}

The logic is the classic Unix one: hash what the user typed with the stored value as the salt, and accept if the result equals the stored value. The detail that matters is the salt line. A stored value of * is one character long, so pw_password[1] is the terminating zero, and the salt stays NULL.

With a NULL salt, xcrypt() calls pick_salt(). That function exists so that sshd spends the same time on accounts with no real hash as on accounts with one; otherwise the response time would tell an attacker which accounts have passwords. It walks the password database and borrows the prefix of the first hash that starts with $:

strlcpy(salt, "xx", sizeof(salt));
setpwent();
while ((pw = getpwent()) != NULL) {
    if ((passwd = shadow_pw(pw)) == NULL)
        continue;
    if (passwd[0] == '$' && (p = strrchr(passwd+1, '$')) != NULL) {
        typelen = p - passwd + 1;
        /* (bcrypt case omitted) */
        strlcpy(salt, passwd, MINIMUM(typelen, sizeof(salt)));
        explicit_bzero(passwd, strlen(passwd));
        goto out;
    }
}

So on a server where the alpine account has * and the root account has a $6$ hash, a login attempt as alpine is hashed as SHA-512 with root's salt. Then the result is compared with *. Nothing here is wrong on its own. The comparison is only safe as long as crypt() cannot return *.

What musl's crypt() returns on failure

musl's SHA-512 implementation, in src/crypt/crypt_sha512.c, refuses long keys:

#define KEY_MAX 256

/* in sha512crypt(): reject large keys */
for (i = 0; i <= KEY_MAX && key[i]; i++);
if (i > KEY_MAX)
    return 0;

The limit is reasonable: SHA-crypt does work in proportion to the key length on every round, so an unbounded key is a cheap way to burn CPU. The problem is what the public wrapper does with that failure:

p = sha512crypt(key, setting, output);
/* self test and stack cleanup */
q = sha512crypt(testkey, testsetting, testbuf);
if (!p || q != testbuf || memcmp(testbuf, testhash, sizeof testhash))
    return "*";
return p;

On any failure it returns the string "*". The SHA-256 code does the same. I checked it on Alpine 3.22.8 with a ten-line C program that calls crypt() with keys of 256, 257 and 1024 bytes:

salt=$6$  len=256  -> $6$$.li6TVmnFwaNje3g...
salt=$6$  len=257  -> *
salt=$6$  len=1024 -> *
salt=$5$  len=256  -> $5$$lML5nAh9pjF4vPnH...
salt=$5$  len=257  -> *
salt=$1$  len=257  -> $1$$oiNhWHvhmJpyzoQX...
salt=xx   len=257  -> xxJJqYuu8A9oE

Up to 256 bytes you get a hash. From 257 bytes on, SHA-256 and SHA-512 return *. MD5 and traditional DES carry on hashing, which is why the bug needs a $5$ or $6$ hash somewhere on the system for pick_salt() to borrow.

Putting it together

  1. A client asks to log in as an account whose password field is *, and sends a password longer than 256 bytes. sshd caps passwords at 1024 bytes, so the window is 257 to 1024.
  2. The stored value is one character, so sshd passes no salt, and pick_salt() returns the $6$ prefix of another account.
  3. musl rejects the key as too long and returns "*".
  4. sshd compares "*" with the stored "*". They are equal, and the login succeeds.

No credential is stolen and no key is needed. The attacker gets a shell with whatever rights the target account has.

Accounts locked with ! are not affected through this path. The stored value ! is also one character, so the salt is borrowed in the same way, but "*" does not equal "!", so the comparison fails.

Why glibc systems are not affected

Most glibc distributions get crypt() from libxcrypt. I ran the same check on Debian 13:

$6$  256  -> $6$$.li6TVmnFwaNje3g...
$6$  257  -> $6$$VVoAsM9yOuDXnTJT...
$6$  512  -> *0
$6$  1024 -> *0
setting "*0"  -> *1

libxcrypt accepts longer keys, up to 511 bytes, but the real difference is the failure value. It returns *0, and when the setting itself starts with *0 it returns *1. The libxcrypt crypt(3) manual says the invalid hash "will not compare equal to setting", and that this is "chosen to make these applications fail closed when an error occurs". The usual caller passes the stored hash as the setting, so a failure can never match it. And because the token is always two characters, it cannot match the one-character * either. musl's failure value is that one character, and it happens to be the most common marker for "no password".

That is the whole bug in one sentence: the error value of one library was a valid value in the data another program compared it against.

The fix in OpenSSH 10.6p2

The commit by Damien Miller is short. The part that closes the bypass is a minimum length for the stored hash:

+#define MIN_PASSWORD_HASH_LEN    4
 #define MAX_PASSWORD_LEN    1024
...
-    return encrypted_password != NULL &&
+    ret = encrypted_password != NULL &&
+        strlen(pw_password) >= MIN_PASSWORD_HASH_LEN &&
         strcmp(encrypted_password, pw_password) == 0;
+    freezero(pw_password, strlen(pw_password));
+    return ret;

No real hash is shorter than four characters. Even a traditional DES hash is 13. So a stored marker such as *, ! or !! can no longer match anything, whatever crypt() returns. The rest of the commit makes shadow_pw() always return a heap copy that the caller wipes with freezero(), so the hash does not linger in memory.

The release notes state the maintainers' view plainly: "We consider the root cause of this bug to be outside sshd, but it is exploitable via sshd and can be avoided there." That is a fair reading. The check belongs in sshd anyway, because sshd is the program making the security decision, and it cannot assume every libc fails the way glibc does.

Why Alpine cloud images matter

SAFE Security points out that the official Alpine cloud images from 3.18.11 to 3.24.3 create an alpine account with * as its password field and passwordless doas, so a login as alpine leads straight to root. A fresh image is not exploitable, because no account has a $5$ or $6$ hash for pick_salt() to borrow. It becomes exploitable the moment someone sets a password on any account, for example a root password for the serial console, and password authentication is on.

This is a good example of how two harmless settings combine. Neither "set a console password" nor "leave password authentication on" looks dangerous alone.

Checking your systems

Run these as root on each musl host. First, the sshd build and configuration:

sshd -V
ls /lib/ld-musl-* 2>/dev/null && echo "musl"
sshd -T | grep -Ei '^(usepam|passwordauthentication|permitrootlogin) '

A build without PAM does not print a usepam line at all. Both a missing line and usepam no mean sshd checks passwords itself; only usepam yes avoids the vulnerable function.

Then the accounts. The first command lists accounts that have * and a login shell. The second shows whether any SHA-crypt hash exists for pick_salt() to borrow:

# Accounts with "*" and a shell that is not nologin or false
awk -F: 'NR==FNR { if ($2 == "*") star[$1]; next }
         ($1 in star) && $7 !~ /(nologin|false)$/ { print $1, $7 }' \
    /etc/shadow /etc/passwd

# Number of SHA-256 or SHA-512 hashes on the system
awk -F: '$2 ~ /^\$[56]\$/' /etc/shadow | wc -l

If the first command prints an account, the second prints a number above zero, sshd is older than 10.6p2 and password authentication is on, the host is exposed.

Expect root in that list. In the Alpine 3.22 container image, root's password field is *. The default PermitRootLogin without-password refuses password logins for root, so root is safe by default, but a host that changed it to yes is exposed through root itself. Accounts created with adduser -D get ! and are not affected. Remember that AllowUsers, DenyUsers and Match blocks can still stop a given account from logging in.

To look for past use, search the logs for password logins to those accounts. On Alpine, sshd logs to /var/log/messages by default:

grep 'Accepted password for' /var/log/messages

sshd does not log the length of a password, so you cannot see the long password itself. The useful signal is a successful password login to an account that has no password.

What to do

Upgrade, then restart sshd. Alpine published these fixed versions of the openssh package:

Alpine branchFixed version
edge10.6_p2-r0
3.2410.3_p1-r2
3.2310.2_p1-r1
3.2210.0_p1-r11
3.219.9_p2-r1
3.209.7_p1-r6
3.199.7_p2-r5 or 9.6_p1-r3
 
apk update && apk upgrade
rc-service sshd restart

The restart matters. Upgrading the package replaces the file on disk, but the sshd that is already running keeps the old code until it restarts. For containers, rebuild the image and redeploy it; upgrading a running container does not survive the next restart.

If you cannot upgrade today, turn off password authentication. Most servers should have it off anyway. Make sure your key login works first, in a second session, so you do not lock yourself out:

# In /etc/ssh/sshd_config, and in any Match block that turns it back on
PasswordAuthentication no
sshd -t                                    # syntax check
sshd -T | grep -i '^passwordauthentication '
rc-service sshd restart

Then reduce what one login can reach. Review accounts with passwordless sudo or doas, keep SSH off the public internet where you can, and put it behind a VPN or a bastion host. None of that replaces the patch, but it limits the damage of the next bug like this one.

What I take away as a developer

I write Python services, not SSH daemons, but this pattern turns up everywhere: a function signals failure with a value that could also be a valid result. A -1 that is also a valid index, an empty string that is also a valid name, a "*" that is also a stored password marker. The caller checks the result against data, and the error slips through as a match.

  • Make errors impossible to confuse with data. Raise an exception, return None, or return a result type. If a sentinel string is unavoidable, choose it so it can never equal a valid value, as libxcrypt does.
  • Validate the shape before comparing. A hash has a known format and length. Checking it before == is exactly what the OpenSSH fix does.
  • Read the failure contract of every dependency. Two libraries can implement the same function name and fail in different ways. Code that is correct on glibc was wrong on musl.
  • Test with boundary inputs. A test with a 257-byte password on a musl build would have caught this. Inputs just past every documented limit are cheap to add to a test suite.

Final thought

Nothing in this bug is exotic: no memory corruption, no race, no cryptography broken. Two pieces of code that were each reasonable on their own disagreed about what "*" means. Those are the bugs I find most worth reading about, because they are the ones I could write myself.

If you run Alpine anywhere, check today: upgrade, restart sshd, and turn off password authentication on servers that do not need it.
